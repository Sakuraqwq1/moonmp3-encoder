# 阶段 1 进度记录

## 2026-11-03（下午）：big_values + 真实量化，正弦 SNR 10.06 → 21.73 dB

### 做了什么

- **`src/mp3/huffman_tables.mbt`**（生成物）+ `tools/huffman_tables.py`：15 张
  big_values 表，取自 `hajimehoshi/go-mp3`（Apache-2.0）。上游存的是解码侧二叉树，
  脚本把它确定性地展开成 `(x, y) -> (码长, 码字)`，并在写出前做三重校验：
  每张表 Kraft 和 = 1（完整前缀码）、无码字冲突、表尺寸是 2/3/4/6/8/16 方阵。
- **MPEG-1 没有 linbits**：两处独立来源一致——go-mp3 的 `huffmanMain` 里 0–15 号表
  linbits 全为 0，minimp3（CC0）的 `g_linbits` 前 16 项也全为 0（1/2/3/4/6/8/10/13
  属于 16–23 号表，那是 MPEG-2 的）。所以 **`|is| ≤ 15` 是 MPEG-1 的硬上限**，
  量化器必须按这个上界选增益，`MaxQuantLevel = 15` 就是它。
- **`src/mp3/huffman.mbt`**：pair 写入（含符号位）、区域字段、表选择（先按 extent
  过滤、再按位代价取最小）、count1 尾部、`GranuleInfo::big_values`。
- **`src/mp3/quantize.mbt`**：删掉"半峰硬门限"，改成真正的 `global_gain` 搜索。
  `GranuleQuantiser` 预计算 `|xr|^(3/4)`，于是可以对十几个候选增益做"重建误差最小"
  比较而不是"够用就停"——这是这一步把 SNR 从 16.4 拉到 21.7 的关键。
- **`encode()`**：big_values + count1，`part2_3_length` 用真实位计数，并且逐 granule
  断言"写入位数 == 计划位数"，防止边信息与实际主数据脱节。
- **奇数子带修正改成纯倒序**：`tools/odd_band.py` 把每个候选映射装进
  `odd_band_value` 重新编码实测，结果是 identity −2.8 dB、
  "倒序 + 交替变号" −1.7 dB、**纯倒序 +16.0 dB**。上一版那半个 bin 的变号虽然让
  频率看起来正确，却把波形毁了。

### 三个已知缺陷（写清楚，别让接手的人踩）

**先纠正一个容易犯的错**：只抽查 440/880/3000/8000/12000 Hz 会以为一切正常。
`tools/sweep_snr.py` 扫过整个频谱，结果是**只有子带中心附近健康**：

| 频率 | 子带 | SNR | 解码主频 |
| ---: | ---: | ---: | ---: |
| 440 | 0 | 21.73 | 438.7 |
| 560 | 0 | 13.30 | 559.9 |
| 620 | 0 | 7.58 | 619.1 |
| 655 | 0 | 3.94 | 654.1 |
| 670 | 0 | 0.68 | 707.9 |
| 685 | 0（边界 689） | **−2.08** | 694.4 |
| 700 | 1 | −1.03 | 678.3 |
| 720 | 1 | 3.21 | 718.7 |
| 760 | 1 | 7.53 | 759.0 |
| 880 | 1 | 20.63 | 880.2 |
| 1000 | 1 | 15.95 | 1001.3 |
| 1300 | 1 | 7.93 | 1300.1 |
| 1360 | 1 | 0.41 | 1397.0 |
| 1390 | 2（边界 1378） | −0.72 | 1367.4 |
| 2000 | 2 | 7.52 | 1999.9 |
| 3000 | 4 | 17.88 | 3001.2 |
| 4000 | 5 | 13.90 | 3999.8 |
| 6000 | 8 | 16.50 | 5999.7 |
| 8000 | 11 | 18.13 | 7999.6 |
| 12000 | 17 | 20.92 | 11999.4 |

结论：**距离子带边界约 ±100 Hz 以内的音会塌**，31 个边界乘起来约占频谱的三成。
这比"只有 660 有一个带边缘问题"严重得多，必须修好再拿数字去申报。

1. **根因**：MPEG-1 原型滤波器过渡带很宽，边界附近的音能量被劈到两个子带上；伪 QMF
   的奇数子带在带内频谱是反的，编码器用倒序修正（`odd_band_value`）。倒序对**带内**内容
   正确，但会把子带边缘的能量搬到带内另一端，破坏相邻带之间的混叠抵消。
   **解法**：把分析滤波器组的**折叠形式**按规范写对——现在的"加窗 + 8 块按列求和"
   是规范求和式的直和等价式，丢掉了折叠带来的带间相位关系。
   判据：修好后 `tools/odd_band.py` 的扫描里 identity 应为最优，且 685/1390 Hz 的 SNR ≥ 20 dB。
2. **奇数子带**偏低（1000 Hz 15.95、8000 Hz 18.13 而偶数带的 3000/12000 有 17.9/20.9），
   根因同上。
3. **立体声那组数字不是串扰**：左右频率各自正确（438.7 / 659.5 Hz），偏低是因为 660 Hz
   踩在缺陷 1 上，且立体声每 granule 主数据预算更紧（762 位）。

已经试过但**不对**的三条路（别重复）：合成滤波器组直转置（选择性掉到 0.33–0.76）、
块内镜像折叠（相邻带漏 4 dB）、倒序 + 交替变号（频率对、波形毁，−1.7 dB）。

**线域置换已经用尽**。`tools/odd_band.py` 把 8 个候选全部实测过（440 / 685 / 1000 / 1390 Hz）：

| 候选 | 440 | 685 | 1000 | 1390 | 最差 |
| --- | ---: | ---: | ---: | ---: | ---: |
| identity | 21.73 | 0.70 | −2.71 | 1.99 | −2.71 |
| reverse17（当前） | 21.73 | −2.08 | 15.95 | −0.72 | −2.08 |
| reverse17 + 交替变号 | 21.73 | −2.07 | −1.45 | 9.82 | −2.07 |
| reverse17 + 交替变号(偶) | 21.73 | 17.07 | −1.49 | −0.64 | −1.49 |
| reverse18 | 21.74 | 0.74 | 0.15 | 6.16 | 0.15 |
| reverse_edges_intact | 21.73 | 0.70 | 15.95 | 2.00 | 0.70 |
| reverse_negated | 18.02 | **17.92** | 16.11 | **11.10** | **11.10** |
| reverse18 + 交替变号 | 21.71 | 0.66 | −0.15 | 5.29 | −0.15 |

读法：`reverse_negated`（倒序 + 整带取负）把边界救到 11–18 dB，但把 440 Hz 的结果从
21.73 压到 18.02——**没有任何线域置换能同时满足带内与带边缘**。这说明问题不在映射，
而在分析滤波器组本身缺少规范的折叠结构（带间相位关系）。当前保留 `reverse17`
（保住 440 Hz 的 21.73 dB 头条指标），并把 `reverse_negated` 作为已知的折中记在这里。

### 下一步

1. 把分析滤波器组的折叠形式写对（上面三条缺陷的共同根因），优先级最高。
2. scalefactor band 表 + 逐带 scalefactor：把每带自己的步长拉开。
3. 补 `chirp` / `impulse` / 满幅用例（满幅 99% 时解码峰值 1.150，有削波风险）。

## 2026-11-03（上午）：PCM → 频线 → 位流打通（首个可听链路）

### 做了什么

- **分析窗表**：`src/mp3/window.mbt`，512 个 ISO/IEC 11172-3 Annex B 系数，
  取自 `hajimehoshi/go-mp3`（Apache-2.0，blob 与 SHA-256 记在 `docs/provenance.md`）。
  `tools/window_table.py` 可复现并逐项校验，`--check` 当门禁用。
- **分析滤波器组**：`src/mp3/analysis.mbt`。
  `S[m] = sum(n) x[n] C[n] cos((16 + n mod 64)(2m + 1) pi / 64)`，512 点滑窗 + 32 子带。
- **长块 MDCT**：同文件。36 点正弦窗、18 条输出线，符号与频线顺序按规范。
- **量化**：`src/mp3/quantize.mbt`。把每个 granule 压到 count1 能表示的 -1/0/1，
  `global_gain = 210 + 4 log2(peak)`；带预算控制，系数过多时抬高门限而不是撑爆帧。
- **`encode()` 真正编码**：公开签名与帧布局不变，主数据不再全零。
- **CLI**：新增 `sine`（内部生成正弦，可任意长）、`encode`（base64 PCM）、
  `lines`（导出一个 granule 的 576 条频线）；`tone` 支持逗号分隔的多条频线。
- **量具**：`tools/probe_lines.py`（频线→频率实测）、`tools/analysis_ref.py`
  （numpy 独立参考 + 逐线比对）、`tools/window_table.py`（窗口表来源校验）。

### 三个必须记住的坑

1. **分析滤波器组的折叠不能想当然。** 先用"块内镜像折叠"写，滤波器组看起来正常工作、
   位流也合法，但每个相邻子带漏进 4 dB：440 Hz 正弦的能量分散到子带 0/1/2/4/6，
   解码主频跑到 1816 Hz。改成按定义式直接求和（窗 → 8 块按列相加 → 32×64 矩阵）
   之后，344 Hz 单音在子带 0 的能量占比 0.9996。**折叠只是这个求和的优化，
   写错了不会报错，只会"能出声但频率不对"。**
2. **奇数子带频谱是反的。** 分析滤波器组对奇数子带的输出在带内镜像：
   1000 Hz 会落到 subband 1 的 bin 10（应 8），解码成 1066–1077 Hz；
   8000 Hz 解码成 7847.66 Hz。修法是奇数子带把 18 条线倒序并交替变号
   （`analysis.mbt` 里有注释）。规范从解码器那头描述同一件事：`frequency inversion`。
3. **重复单线探针只能探到偶数线。** 见 `docs/line-frequencies.md`：
   恒定频谱让子带信号退化成周期 18，能量只落在 76.5625 Hz 网格上，
   所以 line 11 和 line 12 都测出 459.375 Hz。这不是解码器错，是探针退化。

### 现在的边界

- `big_values` 恒为 0，`part2_3_length = 576 + 非零系数个数`，无 scalefactor。
- 每条频率线只有 ±1，因此宽带素材、瞬态、多音的音质都很粗：440 Hz 正弦的
  SNR 只有 10.06 dB。
- 立体声左右独立处理，未做联合立体声；预算按 `(帧位数 - 32 - 边信息) / (2 × 声道)`
  平均分配，系数过多时量化器抬高门限自保。
- 未做 bit reservoir，`main_data_begin` 恒为 0。

## 2026-11-02：count1 位流竖切完成

### 做了什么

- 新增 `src/mp3/count1.mbt`：count1 Huffman 表 B 写入器。
  - 每 4 个 `-1/0/1` 系数生成一个 4 位非零掩码。
  - 码字为掩码的 4 位补码（`15 - mask`）。
  - 每个非零系数追加 1 位符号位，1 表示负数。
- 新增 `src/mp3/main_data.mbt`：固定频谱测试编码器。
  - 每个 granule 都写入同一组 576 个 count1 系数；
  - `big_values = 0`、不传 scalefactor、`count1table_select = 1`；
  - `main_data_begin = 0`，每帧完全自洽；
  - 写帧前预先检查容量，越界直接拒绝。
- CLI 新增调试命令 `tone`：`tone [frames] [line] [gain] [channels]`。

这不是 PCM 编码器，也不改变 `encode()` 的现有行为；它只验证 Huffman、边信息、主数据、帧封装和独立解码器之间的完整通道。

### 验证证据

单条非零频线 `line=12`、4 帧、单声道、`global_gain=210`：

```bash
moon run cmd/main -- tone 4 12 210 1
python tools/mp3dump.py target/tone-line12.mp3 --first 1 --verbose --strict
python tools/spectrum.py target/tone-line12.mp3 --top 5
```

结果：

- `part2_3_length = 577`（576 个掩码位 + 1 个符号位）；
- 4 帧、1671 字节、128 kbps CBR、`mp3dump --strict` 无警告；
- libsndfile 解码出 4608 个样本；
- 解码峰值约 1.0065，主频 459.393 Hz。

幅度校准时将 `global_gain` 降到 206：

- 解码峰值约 0.503，RMS 约 0.333；
- 主频仍为 459.393 Hz。

频线映射探针说明：count1 输入索引并不是直接等于输出 FFT 的线性频点；它经过 Layer III 的合成滤波器组。当前实测 line 11/12 都落在约 459 Hz。这个竖切的目标是位流与帧封装正确，不是建立最终 PCM→频线映射。

### 回归保护

`tools/selftest.py` 新增两条固定频谱用例，锁定：

- 每帧每 granule 的 `part2_3_length = 577`、`big_values = 0`、`count1table_select = 1`；
- 解码长度 4608、峰值在 0.3–0.6、主频 459.375 Hz ±15 Hz。

### 下一步

从这里开始接 PCM 分析路径：先实现多相分析滤波器组，再做长块 MDCT，最后把 576 条频线接到现有 count1 路径。`tone` 命令只保留为位流调试入口，不把它当真实编码功能。
