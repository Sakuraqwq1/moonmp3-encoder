## 6. 建议的开工顺序

### 第 0 步：先建一把尺子（半天，不要跳）

输入频线索引与输出频率的映射还没测准。之前 line 11 和 line 12 都测出约 459 Hz，两次结论互相矛盾——原因是 4096 点 FFT 在低频分辨率不足，且**位流里的频线是子带优先（subband-major）顺序**，不是线性频点。

在做分析滤波之前，先把探针做干净：长样本（≥16 帧）、8192 点以上 FFT、逐条扫描前 24 条频线，输出一张实测映射表存进 `docs/`。**没有这张表，后面出现"能出声但频率不对"时无法定位是 MDCT 错还是映射想错。**

### 第 1 步：解决 `C[512]` 分析窗表的合法来源（阻塞项）

- 只能依据 ISO/IEC 11172-3；**绝不打开 LAME 或 shine**（均 LGPL）。
- 拿到后在 `docs/provenance.md` 记录来源、许可证、校验值，格式参照已有的 count1 表条目。
- 拿不到就停下来报告，不要用"看起来差不多"的窗凑。

### 第 2 步：分析滤波器组 + Python 黄金参考

用 numpy 按规范公式独立写一份参考实现，导出中间数组，和 MoonBit 输出逐项比最大误差。先单声道、先固定输入。

### 第 3 步：36 点 MDCT

每个子带 36 点窗、18 点输出，接重叠。**符号和频线顺序是高频错误点**，必须和 Python 参考对齐。

### 第 4 步：量化 + Huffman

先只做 count1 能覆盖的小幅度信号（`-1/0/1`）跑通"PCM → 频线 → 位流 → 出声"，再补 big_values 表和量化迭代。

### 第 5 步：立体声、多音、边界

最后才是 `sine440_stereo_1s`、`multitone_mono_1s`、`chirp`、`impulse`。

## 7. 红线

1. **不读、不移植 LAME / shine / libavcodec 源码**。libsndfile/mpg123 只能当解码 oracle，不能从中抄编码逻辑。
2. **不改已稳定的帧头、边信息布局、CBR 帧尺寸器的既有行为**，除非测试证明有 bug。
3. **`encode()` 的公开契约不变**：交织 `Int32`、44100 Hz、1/2 声道、16-bit 范围。
4. **阶段 1 不做**短块、联合立体声、VBR、心理声学模型。
5. **不 bump 版本、不打标签、不发布 mooncakes**——由项目所有者决定。
6. **不要为了"看起来功能多"扩大范围**。
7. **失败模式是静默的**：错误不抛异常，只出噪声或静音。每个模块必须有数值参考，不能靠"听着差不多"。
